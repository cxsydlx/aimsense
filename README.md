# AimSense · 人物瞄准实验室

一个**本机离线**的瞄准灵敏度校准工具：把"手感"变成可重复的测量，用固定口径的计时试块（trial block）比较不同灵敏度档位，给出**有证据的推荐**，并把过程数据留成可审计、可训练的样本。

- 平台：Windows 10/11 x64 · WPF（`net10.0-windows`）· C# 12
- **零第三方运行时依赖**：不引用任何 NuGet 包；唯一的构建期依赖是打 MSI 用的 WiX（见「构建」）
- **完全离线**：当前版本**没有任何联网代码**，不上传任何数据（见「数据与隐私」）

---

## 1. 它解决什么问题

FPS 里"这个灵敏度是不是更高"通常靠感觉，换一次设置要打几小时才能有模糊结论，而且**记忆和疲劳会系统性地骗你**。AimSense 把这件事变成一个实验：

1. 用**固定时长、固定目标序列、固定难度**的试块采集表现；
2. 用**统一公式**把每一块变成分数（不看你主观"感觉不错"）；
3. 在对数空间里**成对比较**相邻档位，只有差异超过噪声（标准误）才认为有证据；
4. 最后给出 `cm/360` 推荐值，并列出它依赖的每一块证据。

**刻意不做的事**：测试过程中**不显示"当前最佳"**。实时反馈会让人下意识地去迎合那个数字，把测量变成表演——所以只有结束时才出推荐。

## 2. 核心概念

| 概念 | 含义 |
|---|---|
| **cm/360** | 转身 360° 所需的鼠标移动距离（厘米）。**跨游戏唯一可比的量**，也是本工具内部搜索的维度 |
| 游戏灵敏度 | 各游戏自己的数值。工具通过 `cm/360 = 360 × 2.54 ÷ (DPI × 灵敏度 × yaw)` 与之互换 |
| **yaw**（度/计数） | 游戏引擎把 1 个鼠标计数转成多少度视角。内置 CS2 `0.022`、Valorant `0.07`、Apex `0.022`、OW2 `0.0066` |
| eDPI | `DPI × 游戏内灵敏度`。**同游戏内可比，跨游戏不可比** |
| 模式 | `点击`（静止目标单击）、`跟随`（持续贴靶）、`移动点击`（移动目标单击） |

**搜索起点**不是固定档位表，而是连续推算：`手腕↔手臂`滑杆（纯手臂 52 → 纯手腕 22 cm/360 对数插值）× 跟随类游戏偏低灵敏度（×1.08），并把**鼠标垫宽度当作物理上限**（180° 转身须在垫内完成 ⇒ `cm/360 ÷ 2 ≤ 垫宽 × 0.9`）。你也可以直接填当前灵敏度，工具就以此为起点；搜索范围默认 ±25%（可调 10–60%）。

**自定义游戏**：内置只保证上述 4 个。任何其他游戏都可以在界面里填「名称 + yaw」，同名会覆盖内置系数；不知道 yaw 可以用"已知灵敏度 ↔ 已知 cm/360"反解。**工具不猜系数**——没有 yaw 的游戏不参与换算。

## 3. 界面（六个页面）

| 页面 | 作用 |
|---|---|
| **校准测试** | 设置（DPI / 游戏 / 垫宽 / 起点预览）+ 3D 训练场景 + 推荐依据报告 |
| **手感评分** | 给本次比较过的档位打主观分（0–10）与"更好 / 一样 / 更差"；同时显示训练数据进度 |
| **对局成绩** | 记录真实对局表现（**唯一的外部真值**） |
| **纵向复测** | 登记采用过的档位，之后回到同档位自动算 Δ（**唯一的时间维度信号**） |
| **本地问卷** | 一次性填写的分层变量（握法、垫子类型、每周时长…） |
| **数据与隐私** | 本机数据位置与体积、同意范围、上传预览（**当前仅预览，不发送**）、按类删除 |

导航栏是覆盖式侧栏（鼠标移入展开），动画期间**不改布局**，避免训练场景被反复 Resize。

## 4. 测量与评分口径（版本化，改动必须升版本号）

```
CalibrationScoring.Version = "angular-block-loss-v3"
点击:  100 − 75 × 失败占比 − 25 × 完成度
跟随:  100 − 75 × (1 − 贴靶占比) − 25 × min(平均角误差 / 3, 1)
```

每块的扣分明细、命中/错点/超时、过冲与回拉次数、换向响应与恢复时长都会记录；块的有效性会被独立判定（采样故障、帧间隔超限、窗口失焦等），**无效块不进证据**。

搜索与判定：

- `SensitivitySearch`：在对数空间做**区间收缩 + 三等分**，每轮成对比较相邻档位；
- `PairedEvidence`：差异是否超过 `max(2, √(SE₁² + SE₂²))` 才认定有证据，否则继续增加块数（**重复测量降方差**是刻意设计）；
- `ModeSearch`：块间自适应步进（初始 8%，被拒则减半，下限 3%）；
- 证据版本 `composite-paired-2`：跨模式合成校验后才出最终推荐；
- **难度预检**（Pilot）：最多 3 块、不计分、不进证据；通过门槛（点击 ≥4/6 命中，跟随贴靶 ≥30%）两次后进入正式搜索；未通过会放宽难度（距离 ×0.75、速度 ×0.65、时限 1.5s），过轻松则收紧时限至 0.9s；连续 3 块故障或 20 分钟预算到则中止。

## 5. 3D 训练场景

原生 OpenGL 渲染（`NativeArenaRenderer`）+ WPF 宿主：

- 人物角色由**躯干/骨盆椭球 + 颈肩/四肢圆柱 + 关节球 + 头部与面部板**组成，另有近场 1m 网格与线性雾（34→150m）；
- 目标以**头部角半径**为单位度量误差，保证不同距离/视角下判据一致；
- 动作脚本版本 `character-motion-2`；
- 帧时间被监控：计分期间单帧 >100ms 会**作废该块**并记录原因（宁可不测，也不脏数据）；
- 垂直同步关闭时用主动休眠节流（不空转占满 CPU）；
- 尝试启用 MSAA，若驱动不支持则如实回退并在诊断里写明**（本机实测不可用）**。

鼠标输入走 **WM_INPUT 原始计数**（不经过指针加速与系统缩放），因此"灵敏度"始终以计数为单位、与 Windows 显示缩放无关。

## 6. 数据与隐私

**全部数据留在本机**：`%LOCALAPPDATA%\AimSense\`

```
traces\          逐块 trace（JSONL：逐帧样本 + 块结果 + 帧时间 + 中断记录）
history-v2\      会话摘要
labels\labels-v1.jsonl   只增不改的标签流
model\           离线模型（若有）
games.json       自定义游戏换算系数
install-id       随机 32 位十六进制安装标识（**可一键重置**）
```

- 标签种类：`feel / preference / match / adoption / retest / session / survey / profile`；
- **不采集**硬件指纹、MAC、序列号、计算机名、窗口句柄、进程名；
- 上传（尚未启用）设计为**白名单组装 + 21 条脱敏规则 + 生成后禁传键递归扫描**，命中即抛错；
- **原始逐帧轨迹永不上传**；训练用的是它派生出的聚合与运动学特征；
- 同意闸门是**硬约束**：`ConsentVersion` 仍为草稿时，打包函数直接拒绝执行；
- 「数据与隐私」页可按类删除本机数据（只删勾选项，带二次确认）。

## 7. 离线模型与训练管线

`ml/` 是**开发机上的离线工具链**（不随安装包分发，运行时不需要 Python）：

| 文件 | 作用 |
|---|---|
| `export_dataset.py` | 把 trace / 标签导成 `blocks` / `candidates` / `preference_pairs`（CSV + JSONL）+ 清单与排除原因报告 |
| `train.py` | 训练并产出模型 JSON；**数据量不足时拒绝发布**（而不是发一个假装能用的模型） |
| `bo_duel.py` | 搜索算法对照实验（见下） |

App 侧 `OfflineModel.cs` 只读 JSON 做推理，并按 `FeatureVersion` / `ScoreVersion` / 游戏三重闸门校验，缺失特征会填充并按数量回报。

**特征契约**：`candidate-features-1`（26 项，冻结）；块级派生的诊断量与 15 项逐帧运动学（`Kin*`）单独放在上传包的 `BlockFeatures` 段，不污染契约。

**逐帧运动学**已用 C# 实现（`KinematicsAnalysis.cs`），与 `export_dataset.py` **逐项对拍验证**：真实 94MB trace 上 **45/45 块、675 个值、最大相对差 1.15e-13**；另有黄金向量自检锁定三处易漂细节（`percentile(95)` 线性插值、yaw 差分 mod-360 包裹、速度 `dt ≥ 1e-3` 截断）。

**证据量门槛**：偏好对仅在**两侧都 ≥3 个有效块**时才算可用样本（`MIN_PAIR_EVIDENCE`），其余计入 `low_evidence` 排除统计——避免"2 块的档位"和"13 块的档位"被当成同等证据。

### 搜索算法：为什么没换成贝叶斯优化

对照实验（`bo_duel.py`，合成损失面、同噪声同判据）结论：**BO·EI / BO·Thompson 没有优势**——两者都撞到我设的块数上限、准确率更低（27% / 5% vs 现有策略 33%）。原因是本场景**搜索空间窄、瓶颈是噪声而非搜索效率**。所以保留"区间收缩 + 重复测量 + 成对判据"。这是**被实验推翻的假设**，不是没试过。

**当前数据状态**：标签接近 0 条 → 训练正确地拒绝发布。模型不是代码问题，是**数据还不够**。

## 8. 构建与运行

```powershell
# 编译
dotnet build .\AimSense.csproj -c Debug

# 自包含发布（目标机无需预装 .NET）
dotnet publish .\AimSense.csproj -c Release -r win-x64 --self-contained true -o ..\_publish\AimSense
```

### 打 MSI（WiX v5，按用户安装）

> 三个坑，都是实测踩出来的：
> 1. **必须显式使用 x64 版的 `wix.exe`**（`tools\net472\x64\wix.exe`）。默认解析可能命中 `arm64` 版，在 x64 上起不来，对外报成"拒绝访问/压缩失败"。
> 2. `%TEMP%` 在工作区之外时可能被拒，**把 `TEMP`/`TMP` 指到工作区内**。
> 3. **先 `dotnet publish` 再打包**，否则打进去的是上次的旧负载（会得到一个"看起来新、其实是旧代码"的安装包）。

```powershell
$root = (Get-Location).Path
$env:TEMP = "$root\_tmp"; $env:TMP = "$root\_tmp"
$x64wix = "$root\.nuget\packages\wixtoolset.sdk\5.0.2\tools\net472\x64\wix.exe"
& $x64wix build .\Installer\AimSense.wxs -arch x64 -o ..\_deliver\AimSense-1.1.2-x64.msi `
    -d "PublishDir=$root\_publish\AimSense"
```

安装包特性：按用户路径安装（`%LOCALAPPDATA%\Programs\AimSense`，不需要管理员）、自包含、开始菜单快捷方式 + 可选桌面快捷方式、应用图标、`AllowSameVersionUpgrades`（同版本重装自动替换）。

**卸载**：从「设置 → 应用」，或 `msiexec /x {ProductCode}`。
注意 `msiexec /x "<msi 路径>"` 会报 **1605**（ProductCode 由 WiX 每次构建生成），要用 ProductCode 或从设置里卸。

## 11. 已知限制与未实现（诚实清单）

- **上传链路尚未实现**。已实现的是：本机数据、同意闸门、白名单打包、脱敏与禁传键校验、上传预览。计划的路径是「签名服务器（deviceid + token）签发 → OpenList/WebDAV → 你自己的网盘」，**防篡改设计**为：规范化 JSON + SHA-256 内容哈希 + 每设备只增不改的哈希链（`Seq` + `PrevChainHash`）+ 服务端签名，并在**训练侧验签验链**，不过则丢弃并计数。**注意**：任何客户端签名方案都无法阻止机器主人伪造自己的数据；能做的是"任何局部改动都可被发现"。
- 告知书与用户协议**仍是草稿**，未经法律审阅；`ConsentVersion` 为草稿期间打包函数**拒绝执行**。
- 搜索仍未使用贝叶斯优化（有对照实验说明理由，见 §7）。
- 数据量：可用标签接近 0，模型训练正确地拒绝发布。
- MSAA 在本机不可用（已如实回退并记录）。
- 显示相关的机型特异性（刷新率、独占全屏行为）在不同驱动上可能需要单独验证。
